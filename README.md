# Electronics Sales Analytics 

## Project Overview

This project analyses September 2026 electronics sales data to evaluate revenue performance across products, retail stores, and payment methods. Built using Python, the solution implements a structured data-processing workflow that includes CSV ingestion, numeric validation, transaction cleaning, revenue aggregation, statistical analysis, and automated report generation.

The core analysis is implemented using Python's standard library, with pandas used to independently verify selected calculations. The final output is a formatted sales report containing key metrics, product rankings, high-value transactions, descriptive statistics, and verification results.

## Objectives

- Validate and clean sales data using explicit numeric and business rules.
- Calculate total revenue and revenue breakdowns by product, store, and payment method.
- Identify the top three products by revenue.
- Identify high-value transactions worth at least KES 50,000.
- Calculate mean, median, minimum, and maximum transaction revenue.
- Cross-check selected results using pandas.
- Generate a persistent, human-readable sales report.

## Methodology

### 1. Data Ingestion

The script reads `data/electronics_sales.csv` using Python's `csv.DictReader`. The dataset contains sale IDs, dates, store locations, product names, quantities, unit prices, and payment methods.

Raw records are retained for validation, allowing the script to distinguish between the number of records received, the number accepted for analysis, and the number rejected.

### 2. Numeric Parsing and Data Cleaning

A custom numeric-parsing function validates and converts quantity and unit-price values before they are used in calculations.

The implemented parsing rules are:

| Input condition | Handling |
|---|---|
| Valid numeric values, e.g. `5999` | Converted to a numeric value |
| Correctly grouped thousands, e.g. `1,500` | Commas removed before conversion |
| Recognized currency prefixes, e.g. `KES` and `KSh` | Prefix removed before validation |
| Recognized currency symbols: `$`, `€`, `£`, and `₦` | Symbol removed before validation |
| Leading or trailing whitespace | Stripped before parsing |
| Missing or empty numeric values | Rejected |
| Non-numeric values, e.g. `unknown` or `N/A` | Rejected |
| Incorrect comma grouping, e.g. `12,34` | Rejected |

After parsing, transactions are subjected to additional validation:

- Quantity must be present and numeric.
- Quantity must be greater than zero.
- Quantity must be a whole number.
- Unit price must be present and numeric.
- Unit price must not be negative.

Transactions failing these checks are excluded from the analysis. Their sale IDs and rejection reasons are retained for reporting. Missing values are not imputed, and invalid values are not silently replaced with zero.

A unit price of zero is permitted by the implemented rules. Other fields, including sale date, store, and product, are not independently validated by the current numeric-cleaning workflow.

### 3. Revenue Analysis

Revenue is calculated for each accepted transaction:

`Transaction revenue = Quantity × Unit price`

The script aggregates revenue across four dimensions:

- **Overall:** Total revenue generated by valid transactions.
- **Product:** Revenue contribution of each product.
- **Store:** Revenue generated by each retail location.
- **Payment method:** Revenue associated with each payment method.

Product revenue is ranked in descending order to identify the top three products. Alphabetical ordering is used to resolve ties.

### 4. High-Value Transaction Analysis

Transactions with revenue greater than or equal to **KES 50,000** are classified as high-value.

The report lists each qualifying transaction, including its sale ID, date, store, product, and revenue. It also summarizes the number of high-value transactions recorded by each store.

### 5. Descriptive Statistics

Custom Python functions calculate the following statistics across valid transaction revenues:

- **Mean:** Average revenue per transaction.
- **Median:** Middle value of the sorted transaction revenues.
- **Minimum:** Lowest transaction revenue.
- **Maximum:** Highest transaction revenue.

These measures describe the distribution of transaction values and help reveal the influence of unusually large transactions on the average.

### 6. Independent Verification with Pandas

Pandas is used to recalculate selected metrics from the original CSV using the same parsing and transaction-validation rules.

The script compares:

- Total revenue.
- Revenue by product.
- Top three products.
- Mean and median transaction revenue.

Floating-point results are compared using a tolerance of less than KES 0.005. The report identifies matching or mismatching results. If pandas is unavailable, verification is marked as not checked rather than as a successful match.

## Findings

Using the supplied dataset and the implemented validation rules, the analysis produced the following results.

### Data Quality

| Metric | Result |
|---|---:|
| Source records read | 50 |
| Valid transactions analysed | 46 |
| Transactions excluded | 4 |
| Valid transaction rate | 92% |

The four excluded records contained invalid or missing numeric values: two had invalid or missing quantities, while two had invalid or missing unit prices. Excluding these records prevented unreliable values from affecting the revenue calculations.

### Revenue Performance

| Metric | Result |
|---|---:|
| Total revenue | KES 1,310,812.00 |
| Mean transaction revenue | KES 28,495.91 |
| Median transaction revenue | KES 11,097.00 |
| Minimum transaction revenue | KES 1,499.00 |

The mean transaction revenue is substantially higher than the median. This indicates that larger transactions pull the average upward, so the median provides a useful complementary measure of a typical transaction's value.

## Business Interpretation

The findings highlight three areas of interest:

1. **Product performance:** The HP 15 Laptop was the leading product by revenue. Product-level results can inform inventory planning and sales-performance reviews.
2. **Store performance:** Kisumu Mega Plaza generated the highest revenue in the dataset. Store-level comparisons can help identify differences in sales performance that merit further investigation.
3. **Payment behaviour:** M-Pesa generated the highest recorded revenue among payment methods, making it an important payment channel in this dataset.

The difference between mean and median transaction revenue also shows why sales analysis benefits from multiple statistical measures rather than relying on the average alone.

These findings describe revenue, not profitability. Product costs, operating expenses, stock availability, and customer-level information were not used to establish profit margins or explain the causes of performance differences.

## Assumptions and Limitations

- The source dataset represents electronics sales for September 2026.
- Each valid row is treated as one sales transaction.
- Revenue is calculated as quantity multiplied by unit price.
- Quantities must be positive whole numbers; fractional quantities are rejected.
- Unit prices must be numeric and non-negative; zero is permitted.
- Transactions with missing or invalid numeric values are excluded rather than imputed.
- Recognized currency labels and symbols are treated as formatting; no currency conversion is performed.
- All reported monetary values are expressed in KES.
- The high-value threshold is inclusive of KES 50,000.
- Product rankings are based on revenue, not units sold or profit.
- The current workflow does not independently validate every non-numeric field.
- Pandas verification checks selected calculations using the same business rules; it does not independently validate the source data or the business assumptions.
- The analysis covers one month's dataset and does not establish long-term trends or causal relationships.
